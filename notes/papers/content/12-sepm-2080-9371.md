**2. A.** PERT is the *Program Evaluation and Review Technique*, a network method that uses three time estimates for each activity.

**4. B.** The *economic* feasibility study is the cost-benefit analysis: will the benefits of the system exceed its costs. Technical feasibility asks if it can be built, operational if it will be used, and social (legal) if it is acceptable.

### Group B

@s 10
**Software engineering (5 marks).** Software engineering is the application of a systematic, disciplined, quantifiable approach to the development, operation and maintenance of software (IEEE definition). It applies engineering ideas such as planning, design, measurement and quality control to software work.

**Importance.**
- *Quality:* methods and reviews give reliable software with fewer defects.
- *Cost and time control:* estimation and planning stop projects running over budget and schedule.
- *Large and complex systems:* a team can divide the work into requirements, design, coding and testing.
- *Maintainability:* documentation and good design make later changes easy and cheap.
- *Customer satisfaction:* the system is built to the agreed requirements.
- *Risk reduction:* early feasibility studies and testing expose problems before they become costly.

@s 11
**Requirement analysis (5 marks).** Requirement analysis finds out what the users need from the system and turns it into a clear, agreed specification. The stages are:

1. *Requirement elicitation:* interviews, questionnaires, observation, document study and workshops with the users.
2. *Requirement analysis and negotiation:* remove conflicts, duplicates and unclear needs, and rank them by priority and feasibility.
3. *Requirement modelling:* show them with DFDs, use cases and ER diagrams.
4. *Requirement specification:* write them in the Software Requirements Specification (SRS) as functional and non-functional requirements.
5. *Requirement validation:* users and developers review the SRS for completeness and correctness.
6. *Requirement management:* control changes with version control during the project.

**Or: need for software testing (5 marks).** Testing is running the software to find faults before the user does. It is needed because (1) every program written by people contains defects; (2) a fault found in testing costs far less to fix than one found after delivery; (3) it checks that the software meets the requirements (*verification and validation*); (4) it gives confidence in reliability and security, which matters in banks, hospitals and flight systems; (5) it shows the quality level to the customer, and (6) it protects the reputation of the developer. Typical levels are unit, integration, system and acceptance testing.

@s 12
**Waterfall model (5 marks).** The waterfall model is a linear, sequential model in which each phase must finish before the next begins: requirements, design, implementation (coding), testing, deployment and maintenance. Output of one phase is the input of the next.

| Strengths | Weaknesses |
|---|---|
| Simple and easy to manage | No working software until late in the project |
| Clear milestones and documents at each phase | Changes in requirements are costly because there is no feedback loop |
| Works well when the requirements are stable and well understood | Testing happens late, so errors from early phases are found late |
| Good for small and short projects | High risk and uncertainty for large or long projects |

*Critical view:* it is a good teaching model and fits fixed contracts, but real projects change, so modern teams prefer iterative models.

**Or: spiral model (5 marks).** Proposed by Barry Boehm, the spiral model combines iteration with risk analysis. Each loop of the spiral has four quadrants: (1) *determine objectives*, alternatives and constraints; (2) *identify and resolve risks* by prototyping and analysis; (3) *develop and test* the product of that loop; (4) *plan the next loop* with the customer's review. The radius shows the cost so far and the angle shows progress. It suits large, costly, high-risk projects and allows changes, but it needs risk-analysis skill and is expensive for small projects.

@s 13
**Functional requirements (5 marks).** Functional requirements state *what the system must do*: the functions, inputs, processing and outputs. In the SRS they are listed as numbered statements ("The system shall ...") so that each one can be tested. They differ from non-functional requirements (speed, security, usability), which state how well it works.

*Example: library management system*

| ID | Functional requirement |
|---|---|
| FR1 | The system shall let the librarian register a new member with name, class and phone number. |
| FR2 | The system shall issue a book to a member and record the issue date and due date. |
| FR3 | The system shall calculate a fine for each day a book is returned after the due date. |
| FR4 | The system shall let members search books by title, author or subject. |
| FR5 | The system shall produce a report of all overdue books. |

**PERT (8 marks).** The *Program Evaluation and Review Technique* is a project scheduling method that shows the activities as a network of arrows and nodes, their order, and the time needed. Because durations are uncertain, each activity gets three estimates: *optimistic* (o), *most likely* (m) and *pessimistic* (p). The expected time is

$$t_e = \frac{o + 4m + p}{6}$$

and the standard deviation of an activity is $(p - o)/6$.

**Steps:** list the activities and their predecessors; draw the network; find the expected time of each activity; make the forward pass (earliest start ES and earliest finish EF = ES + t) and the backward pass (latest finish LF and latest start LS = LF - t); the *slack* is LS - ES; the activities with zero slack form the *critical path*, the longest path, which fixes the project duration.

**Example.** Activities A (3 weeks, no predecessor), B (4, after A), C (2, after A), D (5, after B), E (3, after C), F (2, after D and E).

| Activity | Time | ES | EF | LS | LF | Slack | Critical |
|---|---:|---:|---:|---:|---:|---:|---|
| A | 3 | 0 | 3 | 0 | 3 | 0 | Yes |
| B | 4 | 3 | 7 | 3 | 7 | 0 | Yes |
| C | 2 | 3 | 5 | 7 | 9 | 4 | No |
| D | 5 | 7 | 12 | 7 | 12 | 0 | Yes |
| E | 3 | 5 | 8 | 9 | 12 | 4 | No |
| F | 2 | 12 | 14 | 12 | 14 | 0 | Yes |

```figure caption="PERT network of the example. Activity-on-node, durations in weeks; the critical path A-B-D-F is drawn in the accent colour."
from matplotlib.patches import FancyBboxPatch
fig, ax = plt.subplots(figsize=(6.2, 2.5))
ax.set_xlim(0, 12); ax.set_ylim(0, 5); ax.axis('off')
pos = {'A': (1, 2.5), 'B': (4, 4), 'C': (4, 1), 'D': (7, 4), 'E': (7, 1), 'F': (10.2, 2.5)}
dur = {'A': 3, 'B': 4, 'C': 2, 'D': 5, 'E': 3, 'F': 2}
crit = {'A', 'B', 'D', 'F'}
edges = [('A','B'),('A','C'),('B','D'),('C','E'),('D','F'),('E','F')]
for u, v in edges:
    c = ACCENT if (u in crit and v in crit) else INK
    ax.annotate('', xy=(pos[v][0]-0.7, pos[v][1]), xytext=(pos[u][0]+0.7, pos[u][1]),
                arrowprops=dict(arrowstyle='->', color=c, lw=1.8 if c == ACCENT else 1.0))
for k, (x, y) in pos.items():

    ax.add_patch(FancyBboxPatch((x-0.7, y-0.5), 1.4, 1.0, boxstyle='round,pad=0.02,rounding_size=0.15', fc='white', ec=c, lw=1.6))
    ax.text(x, y+0.12, k, ha='center', va='center', fontsize=9, weight='bold', color=c)
    ax.text(x, y-0.27, str(dur[k]) + ' wk', ha='center', va='center', fontsize=6.5, color=INK)

```

The other path A-C-E-F takes 3 + 2 + 3 + 2 = 10 weeks, so C and E can slip by up to 4 weeks without delaying the project, while any delay on A, B, D or F delays it day for day.

**Or: feasibility analysis (8 marks).** *Feasibility analysis* is a short study at the start of a project that decides whether the proposed system is worth building. It is needed because: it avoids wasting money and time on a project that cannot succeed; it compares alternative solutions; it identifies risks early; it gives management facts to approve, change or reject the project; and it sets the scope and budget. The result is a feasibility report.

| Type | Question it answers | Example (school result system) |
|---|---|---|
| Technical | Do we have, or can we get, the hardware, software and skills? | The school computers can run the database software. |
| Economic | Do the benefits exceed the costs (cost-benefit analysis, payback)? | The system costs NPR 150,000 and saves about NPR 80,000 of staff time each year. |
| Operational | Will the users accept and use it in daily work? | Teachers are trained and willing to enter marks online. |
| Schedule | Can it be finished in the time available? | It must be ready before the next terminal exam. |
| Legal | Does it follow the law and the rules (privacy, licences)? | Student data is kept as the education rules allow. |

**Data flow diagram (8 marks).** A DFD is a graphical model that shows how data moves through a system: where it comes from, which processes change it, where it is stored and where it goes. It shows *what* the system does, not *how* or in what order. Symbols (Yourdon-DeMarco): a *circle* or rounded box is a process, a *rectangle* is an external entity (source or destination), two parallel lines is a data store, and an *arrow* is a data flow. DFDs are drawn in levels: level 0 (the context diagram) has one process, and level 1 splits it into its main processes.

**Level-1 DFD of the school library management system.**
